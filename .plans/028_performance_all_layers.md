## 2. Queued — ranked by (impact × frequency) / risk

### Worker
- [ ] **W1 Staff cache TTL 60 s → 600 s + in-isolate cache** (`sheets/mod.rs:38`). ~60 Sheets fetches + KV writes/hour during an event. Trade: revocation latency = TTL. Low risk, but it is an access-control latency choice — note it in the commit.
- [x] **W2 Per-event staff N+1** (`auth.rs::is_event_assigned`): N sequential `get_event_config` KV reads (and N full config parses, CPU) on every `require_auth` request for volunteers only in `staff_emails`. **Done (2026-09-24), neither planned option.** Putting `staff_emails` on `EventMeta` widens what `GET /api/events` returns, and `join_all` keeps the N parses. Instead, `db/event_staff.rs` runs one D1 query (`sql/event_ids_for_staff.sql`, the same comma-delimited predicate as `list_event_meta_page.sql`, ≤20 ids) for candidates, and each candidate is **confirmed against its KV config** before access is granted. D1 is only a locator because its delete and update syncs are non-fatal, so a stale D1 row must not grant. On a D1 miss or error, the old full KV scan still runs: a failed D1 sync must not lock out a volunteer. `worker/tests/security/test_event_staff_lookup.py` runs the SQL against migrated SQLite; the mutant `INSTR(LOWER(staff_emails), ?1)` fails 2 of 4 tests. **Local `wrangler dev` probe** (3 events, D1 and KV deliberately diverged; `GET /api/events`): D1+KV volunteer → 200 (a temporary log confirmed the D1 path); D1-only → 403; KV-only → 200 (slow path); unknown → 403. **Still open:** the denial path (JWT holders who aren't staff) still does the full scan. Trusting a D1 miss would fix it, at the cost of locking out volunteers whose D1 sync failed.
- [ ] **W3 Counting via full attendee list** (6 sites; `public_event.rs:172` on every landing view, `signup.rs` twice per registration). Replace with one aggregate. (`ParticipationType::parse` no longer allocates per attendee, 2026-09-24, plan 030 §3; the list fetch is still the cost.) **Medium risk:** the SQL predicate must equal `ParticipationType::parse` (note `db/dashboard.rs:149` `IN_PERSON_PREDICATE` is narrower). Also: D1 `Ok(empty)` falls back to Sheets for new events → a Google subrequest per public view.
- [ ] **W4 Public GET edge cache** (Cache API, 30–60 s) for `/public/events` and `/public/event/{slug}`; push the `/public/events` filter into SQL (no WHERE, no LIMIT today). **Also a correctness bug:** private-event responses get `public, max-age=120` (`handlers/mod.rs:55-72`). **Correctness half fixed on develop 2026-09-24:** the public layers (`middleware/cache.rs::with_public_cache`) now cache only 2xx responses without a handler-set `Cache-Control`, set `no-store` on errors, and repeat the public policy on a 304; `get_public_event` sets `private, no-store` for private events; `worker/tests/public_cache_policy.rs` (mutant: the old unconditional insert → 2 red). Found alongside it: `.issues/149` (the event-series endpoint lists private and draft events). The perf half (Cache API, SQL filter) is still open.
- [ ] **W5 Credit-ledger release** runs an `INSERT…SELECT` before every balance read (twice per registration). Once per request + indexes `credit_ledger(reason, event_id, email)`, `credit_ledger(organization_id, currency)`. Migration → after RTM#6 (numbering: 0048 is reserved, `.issues/127`).
- [x] **W6 Claim lookup** reads the same attendee row 3–4× (`claim/mint/lookup.rs`); quiz/lock/profile reads are independent → `join!`. **Done (2026-09-24).** The POST executor had the same pattern, so both flows now start with one `claim/mint/helpers.rs::resolve_claim_context`. It makes one unrestricted D1 read (`db::attendees::get_claim_token_row`) that yields the event-id hint (taken before the replay window, as the old peek did) and the window-filtered attendee. That one read answers the walk-in check and the D1 fallback, and on the POST path it also stands in for the D1-first Sheets helper. A D1 error becomes `D1Claim::Unavailable`, which keeps the old D1-retry paths, so a transient error never reads as "not found". `lookup_claim` runs quiz status, the claim-lock KV read and the profile-wallet read with `join!`. **Local `wrangler dev` A/B** (same seed; temporary per-query logs, since removed), D1 row reads per request, old → new: GET pre-registered 3 → 2, GET walk-in 2 → 1, GET expired/unknown 3 → 2, POST pre-registered 3 → 1, POST unknown 3 → 1. Status codes and bodies were unchanged. The remaining GET read is `get_attendee_with_claim_counts`, which is needed for the counts. `worker/tests/claim_single_token_read.rs` has 3 tests; restoring the old `lookup.rs` fails 2 of them. No latency number is claimed (M1).
- [x] **W7 Unknown ticket id → full Sheets fetch, unauthenticated, no rate limit** — done (2026-09-24), differently from the plan. A 404 on a D1 miss would break rows added straight to the Sheet (Sheet→D1 sync is a manual staff action), so the fallback stays and only the **miss** path is limited: `get_public_ticket` splits `get_attendee_by_id` into its D1 and Sheets halves and calls `rate_limit::allow_sheets_fallback` in between (new `SHEETS_FALLBACK_RATE_LIMITER`, 10/60 s per IP, prod 63205 / staging 63305, isolate fallback when unbound). D1 hits never touch it, so a venue behind one NAT can poll freely. Local `wrangler dev` probe: unknown id ×12 → 11× 404 then 429; known id ×15 after that → all 200; other IP → 404. A unit test pins the const to both `wrangler.toml` bindings (mutant staging limit 20 → fails). The one other unauthenticated route that reaches Sheets on an unknown id, `GET /api/deposit/status/{id}` (deadline and checked-in lookups), now uses the same `handlers::ext::get_attendee_for_public` and budget; local probe: 12 deposit-status misses from one IP spend it, and that IP's next unknown ticket gets 429. The remaining `get_attendee_by_id` callers were checked against the router: all sit behind `require_auth` or `require_identity`, except `usdc::recover`, which reads Sheets only after an on-chain deposit verifies.
- [x] **W9 Admin roster**: 3 independent awaits → `join!`; `recent_check_ins` unbounded. **Done (2026-09-24).** `stats.recent_check_ins` now comes from `domain::models::attendee::recent_check_ins`, which keeps the newest `RECENT_CHECK_INS_PER_TYPE` (10) per distinct `participation_type`. It used to carry every checked-in attendee on every dashboard poll. The bound is per type, not a flat 10: the dashboard filters by tab and then takes 10, and a tab is a predicate over `participation_type`, so each tab's newest 10 always sit inside the per-type union (a flat cap would empty the Online tab behind a busy door). Timestamps that are not RFC 3339 are always kept, after the ranked ones, because the browser's `Date.parse` may still rank them. The frontend's `.take(10)` uses the same constant. The credit-balance, credit-applied and THB-settlement batch queries run with `join!`; this is safe because `thb_balances_by_email` only writes `return` rows, which neither sibling reads. The result is O(types × 10) entries instead of O(checked-in); no latency number is claimed (M1). Tests: `domain/tests/recent_check_ins.rs` (5) and the source guard `worker/tests/roster_recent_bounded.rs` (2). Restoring the old handler fails both guard tests. **Local `wrangler dev` + browser check** (seed: 14 in-person check-ins, all newer than 3 online ones): the API sent 13 recent entries instead of 17; the admin In-Person tab rendered the 10 newest in order, and the Online tab (event switched to hybrid) still rendered all 3, the tab a flat cap would have emptied.
- [x] **W10 Dashboard** (2.5 s poll) resolves the event twice, D1 `SELECT *` incl. `form_config`. **Done (2026-09-24).** `GET /api/dashboard/live` no longer reads the `events` row itself. With `?event_id=` it goes straight to `resolve_event_with_access`, whose KV-first `EventConfig` (the read path the rest of the app treats as canonical) supplies name, slug, capacity, deposit and start. Without it, the new `db::dashboard::active_event_id` reads only the id of the row `get_active_event` would pick. The handler 404s when the returned config's id differs from the requested one, because with no events KV binding the resolver returns the global defaults for any id. `in_person_capacity` comes from `EventConfig`, which already maps D1's -1 to `None`; the frontend renders both as unlimited. Per poll: one full-row D1 read fewer on the explicit path, and an id-only query instead of `SELECT *` on the active path. **Local `wrangler dev` + browser check:** explicit, active and unknown (404) ids all behaved as designed, and `/dashboard/live` rendered the name, "Capacity: Unlimited", "Deposit: 15.00 USDC" and the totals. Guard: `worker/tests/dashboard_event_read.rs` (2), which fails 2/2 on the old handler. No latency number is claimed (M1).
- [x] **W11** `resolve_event_by_slug` parses the whole KV index per request. **Done (2026-09-24).** Each isolate keeps a slug → event id `BoundedCache` (cap 16, `event_store/read.rs::SLUG_IDS`). A hit loads that one config and is served only if the config still carries the slug, so there is no TTL and no staleness window: a renamed, reassigned or deleted slug is rejected and falls back to the index scan. A hit skips the index read and the parse of every event's meta; a miss or a rejected hit costs what it did before, plus one config read for the rejection. `BoundedCache::get` now takes a borrowed key, so the lookup does not allocate. **Local `wrangler dev` probe** (temporary logs, since removed; KV seeded with `reseed-kv`): the first request for each slug scanned the index and the second hit the cache; after `PUT` renamed the slug, the old slug's cached id was rejected, the rescan found nothing and the request returned 404 instead of the renamed event. Guard: `worker/tests/slug_cache_guard.rs` (2); dropping the slug comparison fails it. **Known limit:** `PUT /api/events/{id}` does not dedup slugs (only create does), so two events can share one; the index's first match was already arbitrary, and now isolates may also disagree about which one they serve. No latency number is claimed (M1).
- [x] W12 HMAC `importKey` per request → cache the key. **Done (2026-09-24):** `crypto::cached_hmac_key` keeps imported `CryptoKey`s in a per-isolate `thread_local` `isolate_cache::BoundedCache` (cap 4, oldest evicted). Entries are keyed by SHA-256 of the secret, so the cache holds no second copy of it. This covers every `hmac_sha256` caller: JWT sign/verify on each authed request, plus the social-link signing. `worker/tests/isolate_cache.rs` has 4 tests. **Local `wrangler dev` probe** (temporary logs, since removed): 5 `/api/auth/me` calls → 1 import, 4 cache hits; a token signed with the wrong secret still gets 401 on a cache hit. No CPU number is claimed, because M1 is still open.

## 4. Rejected after measurement

- **"Drop the QR KV cache, generation is cheap."** Measured `generate_qr_base64` in `--release`: **0.511 ms native per call** → ~1–1.5 ms in wasm at the edge, on every ticket poll, against a 10 ms cap. That spends the binding budget to save a non-binding one. D4 fixes the actual defects (stale key, 1 h TTL) instead.
- **Stripping `console_log` (−19 KB) / `wasm-opt -O2` (−8.9 KB)** — unchanged from `.issues/135` §6; small next to D1's 385 KB.
